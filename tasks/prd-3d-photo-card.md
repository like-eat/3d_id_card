# PRD：照片生成式数字 3D 名片

**版本：** v0.1  
**状态：** 待确认  
**产品代号：** 3D Photo Card  
**目标端：** 移动端浏览器优先，兼容桌面浏览器

## 1. 产品概述

用户上传 1–3 张能够代表自己的照片，填写姓名、简介和社交链接后，系统生成一张可旋转、可探索的个人数字 3D 名片。

正面和背面保持名片的基本轮廓与信息可读性；从其他角度观看时，名片会展开成由照片主题决定的微缩景观。例如：

- 国家公园照片生成森林、草坡和湖泊；
- 海岸照片生成礁石、沙滩和海面；
- 城市照片生成街区、建筑和灯光；
- 抽象图像生成色彩、几何和粒子构成的空间。

这不是一次性的 3D 建模服务，也不是让 AI 为每个用户重新编写一个网站。产品由以下三部分组成：

1. 固定的名片轮廓与交互框架；
2. 由照片决定的结构化场景配置；
3. 统一的 Three.js 实时渲染引擎。

最终用户通过一个独立网址访问名片，网址可以写入 NFC 标签，也可以通过二维码分享。

## 2. 核心判断

### 2.1 不使用“每次重新生成代码”的方案

每次调用大模型重新生成 React 和 Three.js 项目会产生以下问题：

- 响应时间和推理成本不可控；
- 不同用户得到的技术结构不一致；
- 无法集中修复性能和安全问题；
- 用户修改链接、姓名或颜色时可能需要重新生成；
- 版本升级和内容迁移困难。

### 2.2 采用“AI 生成场景配置，固定引擎负责渲染”

AI 根据照片输出经过 Schema 校验的 `SceneSpec`。Three.js 引擎读取 `SceneSpec` 后组装场景。

```text
照片 + 用户资料
      ↓
图片理解
      ↓
场景规划 Agent
      ↓
SceneSpec JSON
      ↓
固定 Three.js 渲染引擎
      ↓
预览 / 编辑 / 发布
```

首版不需要复杂的多 Agent 自由协作。一个带工具的编排 Agent 即可完成；当任务量或质量要求证明有必要时，再拆分图像分析、场景规划和质量检查角色。

## 3. 目标用户与使用场景

### 3.1 主要用户

- 希望替代纸质名片的创意工作者；
- 参加展会、会议和社交活动的自由职业者；
- 需要展示作品集或个人主页的开发者、设计师与摄影师；
- 希望把社交链接集中到一个有记忆点的页面上的普通用户。

### 3.2 核心场景

**面对面交换名片：**

用户用手机碰触对方手机的 NFC 区域，或扫描二维码，直接打开自己的 3D 名片网页。

**线上分享：**

用户把公开链接发送到微信、社交媒体或邮件中。接收方无需安装 App，即可在浏览器中查看。

**作品展示：**

用户调整照片、场景和镜头后，获得一个可长期更新的个人页面。

## 4. 产品目标

### 4.1 MVP 目标

- 用户可以在不进入代码编辑器的情况下创建一张 3D 名片。
- 用户上传照片后，系统能稳定生成一个与照片主题、色调和氛围相符的 3D 微缩景观。
- 名片正面和背面的姓名、简介与链接清晰可读。
- 用户可以在手机上旋转、缩放和查看场景。
- 用户可以发布独立网址，并获得二维码和 NFC 可写入地址。
- 设备性能不足或 WebGL 不可用时，仍能查看姓名、简介和链接。
- 同一套后台能力可以通过网页表单调用，也可以在后续通过 API 调用。

### 4.2 建议的成功指标

- 代表性测试照片的场景生成成功率达到 90% 以上；
- 用户从上传照片到获得首版预览的中位时间低于 90 秒；
- 已发布名片在中端手机上的默认场景帧率不低于 30 FPS；
- 已发布名片的资料与链接完整率达到 95% 以上；
- 首次访问用户在 10 秒内能够理解“这是名片，并且可以拖动”。

这些指标作为 MVP 的验收方向，正式数值需在设备测试后调整。

## 5. 用户流程

### 5.1 创建流程

1. 用户进入创建页。
2. 上传 1–3 张照片。
3. 填写姓名、职位、一句话简介和个人网站。
4. 添加社交链接，系统根据链接域名显示对应图标和名称。
5. 点击“生成我的名片”。
6. 系统分析照片，显示生成进度。
7. 用户进入编辑预览，可以切换正面、背面和自由视角。
8. 用户可以调整场景类型、光照氛围、色温、镜头高度和植被密度。
9. 用户点击“发布”。
10. 系统生成公开网址、二维码和 NFC 写入地址。

### 5.2 访问流程

1. 接收方点击链接、扫描二维码或用手机碰触 NFC 标签。
2. 页面首先显示姓名、职位和加载状态。
3. 3D 场景加载完成后，页面提示“拖动查看世界”。
4. 用户拖动旋转、双指缩放，点击名片背面查看链接。
5. 链接在新标签页打开，并经过安全校验。

## 6. 用户故事

### US-001：上传照片

**描述：** 作为创建者，我想上传几张代表自己的照片，以便系统生成与自己有关的 3D 场景。

**验收标准：**

- [ ] 支持 JPG、PNG 和 WebP；
- [ ] 支持 1–3 张照片；
- [ ] 单张照片不超过 15 MB；
- [ ] 上传中显示进度；
- [ ] 图片格式或尺寸不合法时显示明确错误；
- [ ] 用户可以删除并重新上传照片；
- [ ] 原始照片默认不公开；
- [ ] 在浏览器中完成端到端上传验证。

### US-002：填写个人资料

**描述：** 作为创建者，我想填写姓名、职位和联系方式，以便接收方能够识别并联系我。

**验收标准：**

- [ ] 姓名和职位为必填项；
- [ ] 简介最多 160 个字符；
- [ ] 个人网站和社交链接只接受 HTTP 或 HTTPS 地址；
- [ ] 支持网站、邮箱、微信、LinkedIn、GitHub、小红书等常见类型；
- [ ] 二维码使用发布后的 HTTPS 地址生成；
- [ ] 表单刷新后能够恢复尚未提交的内容；
- [ ] 在浏览器中验证表单校验和恢复流程。

### US-003：生成场景

**描述：** 作为创建者，我想让系统根据照片自动生成场景，以便不用学习 3D 软件。

**验收标准：**

- [ ] 系统识别照片的主题类型；
- [ ] 系统提取至少 4 个主色和 1 个建议光照氛围；
- [ ] 系统输出通过 Schema 校验的 `SceneSpec`；
- [ ] 无法可靠识别时，用户可以从预设场景中手动选择；
- [ ] 生成失败时可以重试，且不会丢失用户资料；
- [ ] 每次生成结果都保存为可追踪的场景版本；
- [ ] 在浏览器中验证生成成功、失败和重试流程。

### US-004：预览和调整

**描述：** 作为创建者，我想从不同角度查看并调整 3D 名片，以便发布前确认效果。

**验收标准：**

- [ ] 提供正面、背面和自由视角三个入口；
- [ ] 用户可以拖动旋转，并限制镜头避免进入地面以下；
- [ ] 正视图和背视图仍然呈现清楚的名片轮廓；
- [ ] 可调整场景类型、光照、色温和植被密度；
- [ ] 每次调整在 500 毫秒内更新本地预览，不重新调用 AI；
- [ ] 提供保存草稿和恢复上次版本；
- [ ] 在手机和桌面浏览器中验证主要交互。

### US-005：发布和分享

**描述：** 作为创建者，我想把名片发布成链接，以便通过 NFC、二维码或社交软件分享。

**验收标准：**

- [ ] 发布后生成稳定的 HTTPS 地址；
- [ ] 生成可下载的二维码；
- [ ] 提供可直接写入 NFC 标签的网址；
- [ ] 已发布页面只能读取指定版本的数据；
- [ ] 用户修改草稿不会立即改变线上版本；
- [ ] 用户重新发布后线上版本更新；
- [ ] 在浏览器中验证发布、二维码和再次发布流程。

### US-006：低性能降级

**描述：** 作为访问者，我希望在设备性能不足时仍能查看对方信息。

**验收标准：**

- [ ] WebGL 不可用时展示静态封面、姓名、简介和链接；
- [ ] 低性能设备自动降低草密度、阴影和粒子数量；
- [ ] 页面进入后台后暂停不必要的渲染；
- [ ] 尊重系统的“减少动态效果”设置；
- [ ] 网络加载失败时提供普通链接兜底；
- [ ] 在浏览器中模拟弱网和 WebGL 不可用状态。

### US-007：通过 API 创建名片

**描述：** 作为集成方，我想通过 API 创建和发布名片，以便在自己的产品中调用相同能力。

**验收标准：**

- [ ] API 使用异步任务模型；
- [ ] 创建、查询、更新、发布接口具备输入校验；
- [ ] 上传使用短期有效的签名地址；
- [ ] API 返回稳定的错误码和可读错误信息；
- [ ] 公开页面只暴露发布所需数据；
- [ ] API 文档提供完整请求和响应示例。

## 7. 功能需求

### 7.1 名片与资料

- **FR-1：** 系统必须使用接近实体名片比例的固定轮廓，建议长宽比为 1.586:1。
- **FR-2：** 姓名、职位、简介、网站和社交链接必须保存在独立的数据模型中。
- **FR-3：** 名片正面至少显示姓名、职位和头像或主题标识。
- **FR-4：** 名片背面必须包含社交链接或打开链接的明确入口。
- **FR-5：** 社交链接必须校验协议，禁止 `javascript:`、`data:` 和可执行内容。
- **FR-6：** 用户必须能够创建、保存、预览和发布场景草稿。

### 7.2 照片与场景生成

- **FR-7：** 系统必须支持 1–3 张照片的输入。
- **FR-8：** 系统必须识别至少以下场景类型：森林/山地、海岸、城市、抽象。
- **FR-9：** 系统必须从照片中提取主色板、明暗氛围、视觉中心和地平线信息。
- **FR-10：** 系统必须将分析结果转换为经过类型校验的 `SceneSpec`。
- **FR-11：** 当 AI 输出缺失字段或超出允许范围时，系统必须回退到安全预设。
- **FR-12：** 用户必须能够在不重新分析照片的情况下，手动切换场景模板和视觉参数。
- **FR-13：** 系统必须保留最近 5 个场景版本，避免错误覆盖。
- **FR-14：** 照片分析必须异步执行，编辑页可随时离开并稍后返回。

### 7.3 3D 渲染

- **FR-15：** 公开名片必须基于 Three.js 或 React Three Fiber 实时渲染。
- **FR-16：** 场景必须由 `SceneSpec` 驱动，不得为单个名片生成并执行任意源代码。
- **FR-17：** 相机必须支持拖动旋转和限制范围内的缩放。
- **FR-18：** 场景必须支持至少地形、植被、水面或天空、主光、环境光五类图层。
- **FR-19：** 草、花朵和粒子必须优先使用实例化、纹理面片或着色器，不得为每根草创建独立网格。
- **FR-20：** 系统必须根据设备能力选择高、中、低三档质量设置。
- **FR-21：** 页面不可见时必须暂停动画和阴影更新。
- **FR-22：** WebGL 初始化失败时必须显示静态封面和可访问的联系方式。

### 7.4 发布与分享

- **FR-23：** 每个公开名片必须有唯一、稳定、不可猜测的路径标识。
- **FR-24：** 发布操作必须生成不可变版本，并在用户再次发布时更新公开指向。
- **FR-25：** 系统必须生成指向公开 HTTPS 地址的二维码。
- **FR-26：** 系统必须提供 NFC 标签可写入的 HTTPS URL；NFC 标签本身只保存网址。
- **FR-27：** 公开页必须包含页面标题、描述、分享图和基础 Open Graph 元数据。
- **FR-28：** 公开页加载失败时必须显示普通文本联系方式和网站链接。

### 7.5 编辑器

- **FR-29：** 编辑器必须采用移动端优先布局。
- **FR-30：** 编辑时必须提供“查看名片”和“查看世界”两种镜头预设。
- **FR-31：** 参数修改必须先更新本地预览，再显式保存，不得每次修改都调用 AI。
- **FR-32：** 生成中和发布中必须显示明确进度状态，避免用户重复提交。
- **FR-33：** 用户必须能够删除项目及其原始照片。

### 7.6 API 与后台

- **FR-34：** 后台必须提供项目、场景版本、素材和发布记录四类资源。
- **FR-35：** 图片分析、场景规划和资产处理必须通过任务队列执行。
- **FR-36：** 所有 AI 输出必须经过 Zod 或等价 Schema 校验。
- **FR-37：** 原图、处理中间文件和公开资源必须使用不同的访问策略。
- **FR-38：** 公开读取接口不得返回用户邮箱、原始照片路径或后台任务信息。
- **FR-39：** 系统必须记录生成版本、模型版本和模板版本，以便复现问题。

## 8. SceneSpec 数据契约

`SceneSpec` 是 AI、编辑器、存储和渲染引擎之间的核心接口。首版建议结构如下：

```json
{
  "schemaVersion": "1.0",
  "template": "mountain_lake",
  "palette": {
    "primary": "#20372f",
    "secondary": "#708b67",
    "surface": "#d5c5a3",
    "accent": "#8fb4c5"
  },
  "environment": {
    "terrain": {
      "kind": "heightfield",
      "amplitude": 0.42,
      "roughness": 0.55
    },
    "water": {
      "enabled": true,
      "level": 0.18,
      "reflectionQuality": "medium"
    },
    "foliage": {
      "preset": "pine_grass",
      "density": "medium"
    },
    "lighting": {
      "preset": "morning",
      "direction": [0.5, 1, 0.4],
      "fog": 0.18
    }
  },
  "camera": {
    "default": "commercial",
    "allowOrbit": true,
    "minPolarAngle": 0.55,
    "maxPolarAngle": 1.45
  },
  "quality": {
    "target": "auto",
    "maxDrawCalls": 120
  }
}
```

约束：

- 所有数值必须有上下限；
- 枚举字段只能使用已注册模板；
- 模板名不能直接映射为文件路径；
- 不允许 `SceneSpec` 携带任意 JavaScript、HTML 或着色器源码；
- 每次 Schema 升级必须提供迁移逻辑或版本兼容规则。

```text

┌──────────▼───────────┐
│ Application API      │
│ Auth / Projects      │
│ Uploads / Publish    │
└───────┬───────┬──────┘
        │       │
        │       └──────────────┐
        ▼                      ▼
┌──────────────┐       ┌───────────────┐
│ PostgreSQL   │       │ Object Storage│
│ projects     │       │ originals     │
│ versions     │       │ processed     │

└──────────────┘       └───────────────┘
        │

```

### 9.1 模块职责

| 模块 | 职责 | 不负责 |
| --- | --- | --- |
| Web Editor | 上传、表单、预览、参数调整、发布 | 执行任意生成的代码 |
| Application API | 鉴权、项目、版本、素材和发布管理 | 直接运行长时间 AI 任务 |
| Worker | 图片分析、场景规划、资产生成、质量检查 | 向访问者直接提供页面 |
| Scene Engine | 解析 SceneSpec，渲染和优化 3D 场景 | 调用大模型 |
| Public Viewer | 加载已发布版本、处理分享和降级 | 暴露编辑权限 |
| Object Storage | 保存原图、中间产物和公开资源 | 业务状态管理 |

### 9.2 AI 编排方式

MVP 推荐单编排 Agent 加确定性工具：

1. **选择照片工具：** 检查照片清晰度、方向和重复度；
2. **视觉分析工具：** 提取主题、配色、地平线、视觉中心和光照；
3. **模板检索工具：** 从注册模板中选择最接近的场景；
4. **场景规划工具：** 输出 SceneSpec；
5. **校验工具：** 检查 Schema、数值范围和资产引用；
6. **质量检查工具：** 生成缩略图并检查空白、遮挡和构图。

拆分多 Agent 并非 MVP 必需。只有在以下情况出现时再拆分：

- 单个 Agent 的上下文过长，分析质量下降；
- 图像分析、场景规划和性能检查需要独立模型；
- 单次生成耗时无法通过队列和并行工具解决。

## 10. 推荐技术框架

### 10.1 前端

- Next.js + TypeScript；
- React Three Fiber + Three.js；
- Zod 校验共享数据结构；
- CSS Modules 或统一设计令牌，避免场景 UI 和 3D 内容互相争夺视觉重点；
- WebGL 降级静态图；
- 浏览器端 SVG 或 Canvas 二维码生成。

### 10.2 后台

- 与 Next.js 同仓库的后台 API，首版减少部署复杂度；
- PostgreSQL 保存项目、场景版本和发布记录；
- S3 兼容对象存储保存照片和资产；
- 独立 Worker 执行图片分析和场景生成；
- Redis 或受管队列保存异步任务；
- 大模型通过 Provider Adapter 接入，避免绑定单一供应商。

### 10.3 场景引擎

- 使用固定模板注册表；
- 使用高度图、实例化植被和简化水面；
- 使用压缩纹理；
- 对草、花、粒子按距离分级；
- 限制绘制调用和实时阴影范围；
- 公共渲染器与编辑器共用同一套 SceneSpec 解释器。

## 12. API 草案

所有接口以 `/v1` 为前缀。创建和生成采用异步任务。

### 创建项目

`POST /v1/projects`

返回项目 ID 和上传地址。

### 开始生成

`POST /v1/projects/{id}/generate`

返回 `jobId`。服务端执行照片分析、场景规划和质量检查。

### 查询任务

`GET /v1/jobs/{jobId}`

返回 `queued`、`running`、`succeeded` 或 `failed`，以及当前步骤。

### 获取项目

`GET /v1/projects/{id}`

返回用户资料、素材摘要、当前 SceneSpec 和场景版本。

### 修改场景

`PATCH /v1/projects/{id}/scene`

只接受 SceneSpec 中允许用户修改的字段，不重新运行图片分析。

### 发布

`POST /v1/projects/{id}/publish`

将指定场景版本发布到稳定公开地址。

### 获取公开名片

`GET /v1/public/cards/{slug}`

只返回公开资料、公开素材和已发布 SceneSpec。

## 13. 性能要求

- 移动端默认质量档目标为 30 FPS；
- 首屏优先显示姓名和静态封面，再加载 3D；
- 公开页初始资源目标控制在 8 MB 以内，后续可根据真实资产调整；
- 使用压缩纹理和按需加载；
- 草和花使用实例化，禁止独立网格；
- 实时反射仅在高档设备启用；
- 场景离开视口或页面隐藏时暂停渲染；
- 低端设备减少阴影、雾、水面反射和粒子；
- 任何性能档位都必须保留姓名、简介和链接。

## 14. 隐私、安全与内容约束

- 原始照片默认私有，公开页面只引用处理后资源；
- 上传接口校验文件签名、大小和图片尺寸，不只看扩展名；
- 用户删除项目时删除原图、中间产物和公开资源；
- AI 输出只作为结构化数据使用，不直接插入 HTML；
- 所有链接经过协议和域名校验；
- 公开页面不返回用户邮箱、存储路径或内部提示词；
- API 需要有速率限制和任务配额；
- 生成失败日志不得包含不必要的原始图片内容；
- 在隐私政策中说明照片处理方式、保留期限和第三方模型调用。

## 15. 非目标

MVP 不包含以下能力：

- 从任意照片精确重建真实 3D 场景；
- 为每个用户生成一份独立源代码；
- 原生 iOS 或 Android App；
- VR/AR 头显模式；
- 用户上传自定义 3D 模型和着色器；
- 实时多人协作编辑；
- 电商、支付或实体名片印刷；
- 从纸质名片 OCR 自动导入资料；
- 复杂的自由文本生成任意场景；
- 音频、视频或直播内容托管。

## 16. MVP 实施顺序

### 阶段 0：工程骨架

- 建立 Web、Worker、Contracts 和 Scene Engine 目录；
- 定义 SceneSpec 和共享类型；
- 建立示例数据与固定测试照片；
- 建立基础页面路由：
  - `/`：产品入口；
  - `/editor`：创建和预览；
  - `/card/[slug]`：公开名片；
- 建立健康检查接口。

**验证：** 所有包可以类型检查，Web 和 Worker 可以本地启动，示例 SceneSpec 能通过校验。

### 阶段 1：单模板纵向切片

- 完成一个“山地森林”模板；
- 完成照片上传和资料填写；
- 使用固定 SceneSpec 渲染预览；
- 支持拖动旋转和正反面查看；
- 支持姓名、简介和三个链接；
- 完成静态封面降级。

**验证：** 不上传真实 AI 结果也能走通“创建 → 预览 → 分享地址”的完整流程。

### 阶段 2：照片分析与场景规划

- 接入视觉模型；
- 提取主题、颜色、光线和构图；
- 输出并校验 SceneSpec；
- 增加海岸、城市和抽象模板；
- 增加失败重试与手动模板选择。

**验证：** 使用固定测试照片集，连续生成结果符合 Schema，失败时可回退。

### 阶段 3：编辑、版本和发布

- 增加光照、色温和植被密度调整；
- 保存场景版本；
- 发布、撤回和再次发布；
- 生成二维码和 NFC 地址；
- 增加 Open Graph 分享信息。

**验证：** 修改草稿不会影响线上版本，重新发布后线上版本正确更新。

### 阶段 4：开放 API 与生产优化

- 增加 API Key 和异步任务接口；
- 增加对象存储直传；
- 增加配额、日志和错误码；
- 完成低端设备质量分级；
- 增加生成质量检查和运营指标。

**验证：** 外部程序可独立完成创建、查询、修改和发布流程。

## 17. MVP 验收标准

MVP 完成时必须满足：

- [ ] 用户可以上传至少一张照片并填写完整资料；
- [ ] 系统可以生成或选择至少一种与照片相符的 3D 场景；
- [ ] 用户可以拖动、缩放和查看名片正反面；
- [ ] 正视图和背视图能清楚识别为名片；
- [ ] 公开页不需要安装 App；
- [ ] NFC URL、二维码和普通网址指向同一个稳定页面；
- [ ] WebGL 不可用时仍可访问联系方式和社交链接；
- [ ] 手机端弱网和高性能设备均可正常使用；
- [ ] AI 失败不会阻断用户手动选择场景和发布；
- [ ] 同一套后台可通过网页和 API 调用；
- [ ] 用户能够删除项目和相关照片；
- [ ] 所有共享数据结构通过类型检查；
- [ ] 核心流程在浏览器中完成端到端验证。

## 18. 待确认决策

以下决策会影响实施范围，建议在进入编码前确认：

1. **产品形态**
   - A. 先做个人自用版，只服务一个或少数用户；
   - B. 直接做公开 SaaS，允许陌生用户注册和发布；
   - C. 先做带网页界面的内部 API，后续再开放注册。

2. **首版输入方式**
   - A. 只支持照片自动生成；
   - B. 照片自动生成，同时允许手动选择模板；
   - C. 只提供模板和参数编辑，暂不接入视觉模型。

3. **首版部署范围**
   - A. 本地运行，验证体验；
   - B. 部署到公网，具备账号、存储和发布能力；
   - C. 先完成渲染器，网页与后台使用模拟数据。

4. **首版场景**
   - A. 只做森林/山地；
   - B. 同时做森林、海岸、城市；
   - C. 先做一个抽象场景，减少素材成本。

建议默认选择为 **1C + 2B + 3A + 4A**：先做可被程序调用的内部产品，照片自动识别与手动选择并存，本地完成一个森林模板的完整纵切片，再部署和扩展。
